Branch #10 리소스 로드 시스템 어드레서블 개편

Commit
    [Refactor][Client] Key 기반 Meta 검증 플로우 및 텐츠 로딩 규칙 확정

변경 요약
    콘텐츠 Meta 검증 플로우를 Key 기반 서버 API 연동 구조로 전환

    서버 Meta API(/api/meta?Key={Key}) 규칙에 맞춰
    클라이언트 Meta 요청 / 로컬 저장 / 검증 규칙을 통합 정리

    ContentManifest, Catalog, 향후 Bundle까지
    동일한 Meta 검증 규칙을 공유하도록 리소스 로딩 기준선 확정

상세 변경 내용
    1. 콘텐츠 Meta 검증 책임 구조 확정 (Client)
        콘텐츠 검증의 주체는 항상 클라이언트
        서버는 Meta JSON 제공만 수행

        클라이언트 검증 플로우 고정
            로컬 Meta 로드
            -> 서버 Meta 요청 (/api/meta?Key={Key})
            --> sha256 비교
            UpToDate / Outdated / Failed 판정

    2. ContentManifest Meta 검증 규칙 통일
        ContentManifest.verify.metaApi를 Meta API 템플릿으로 사용
            "verify": {
            "metaApi": "api/meta?Key={Key}"
            }

        ContentManifest 자체도 Meta 검증 대상에 포함
            Key = ContentManifest
            → Meta/ContentManifest.meta.json

    3. ContentPath 유틸리티 정비
        서버 Meta URI / 로컬 Meta 경로 생성을 단일 유틸로 통합
        플랫폼 종속 경로 처리 제거
        로컬 Meta 경로 규칙 고정
            Application.persistentDataPath / Meta / {Key}.meta.json
        서버/로컬 경로 혼입 문제 제거

    4. ContentVerifier 구조 고정
        ContentVerifier는 순수 Meta 검증 유틸리티로 유지
        네트워크 실패 / 파싱 실패 / 비교 실패를 명확히 분리
        상태 전달은 ContentVerifyState 단일 구조체로 통합

    5. ContentMetaGenerator 전면 개편
        기존 경로 기반 Meta 생성기 제거
        RemoteDatasRoot 기준으로 모든 콘텐츠 파일을 스캔
        Meta 폴더 제외
        서버 MetaIndex와 동일한 Key 생성 규칙으로 Meta 파일 생성

    6. ResourceManager 책임 범위 명확화
        ResourceManager는 부트스트랩 단계에서
        로컬 Meta 로드 -> 원격 Meta 검증 까지만 수행
        실제 콘텐츠 다운로드 및 교체 로직은
        C_UpdateContent()로 분리하여 후속 구현 예정

    구조적 의미
        리소스 로딩 파이프라인의 검증 기준선 확정
        콘텐츠 경로 구조 변경 없이
        CDN 분리
        번들 분할
        패치 서버 도입
        가능하도록 설계 고정
        서버와 완전히 대칭적인 Meta 프로토콜 확립

비고
    본 커밋은 콘텐츠 검증 단계까지만 포함
    Addressables / 실제 다운로드 로직은 포함하지 않음
    이후 커밋부터는 Outdated 상태를 전제로 콘텐츠 갱신 구현 예정


PR #11 [Need for API Server] Key 기반 Meta 검증 플로우 및 컨텐츠 로딩 규칙 확정
Merged At {} into Main

배경 / 문제
    콘텐츠 업데이트 판단을 클라이언트 단독으로만 처리하면, “서버가 가진 최신 Meta”를 기준으로 한 일관된 검증이 어렵습니다.
    또한 Manifest/Catalog 같은 부트스트랩 데이터의 위치와 검증 규칙이 흔들리면, 이후 모든 로딩/다운로드 로직이 설계 충돌을 일으킵니다.

목표
    서버는 Meta 저장소 + 조회 API 제공 역할만 수행합니다.
    검증 판단 및 다운로드 트리거는 클라이언트의 책임으로 고정합니다.
    ContentManifest 및 Catalog의 Meta 기반 업데이트 규칙을 불변 규칙으로 확정합니다.

변경 요약
    1) 서버 프로젝트 역할 재정의
        솔루션/프로젝트 명칭 변경
            DatabaseServer → ApiServer
        서버의 책임 범위 고정
            Meta 제공: O
            검증 판단: X
            파일 다운로드: X
            업데이트 수행: X

    2) Key 기반 Meta 조회 API 도입
        클라이언트는 “Key”를 기준으로 서버에 Meta를 요청합니다.
        서버는 요청된 Key에 대응하는 Meta JSON만 반환합니다.

    3) 클라이언트 콘텐츠 로딩 규칙 확정(전역 불변)
        Manifest는 부트스트랩 데이터로 취급하며 항상 로컬(persistent)에 존재해야 합니다.
        로컬에 없으면 Resources/Data/DefaultManifest에서 복사하여 생성합니다.
        검증 대상은 항상 Meta입니다.
        Meta가 Outdated일 때만 본문(Manifest/Catalog 등)을 다운로드하여 교체합니다.
        Manifest 자체를 “검증 대상”으로 간주하지 않습니다.
        Catalog도 동일하게 “Meta 검증 → Outdated 시 본문 다운로드” 규칙을 따릅니다.

        API 서버 스펙(개념)
            Minimal API 기반
            “Key → Meta JSON” 조회 전용
            응답은 단순 JSON(캐시 가능한 정적 성격)

        영향 범위
            서버: Meta 제공 전용으로 역할 축소 및 구조 확정
            클라이언트: Meta 비교 및 업데이트 판단 로직을 서버 연계 플로우로 확장 가능해짐
            이후 작업: 클라이언트 측 “Meta 요청 → 비교 → Outdated 시 다운로드” 구현이 다음 단계로 자연스럽게 이어짐

    테스트 / 검증
        서버에서 특정 Key에 대한 Meta 조회 응답 확인
        존재하지 않는 Key 요청 시 처리 확인
        클라이언트의 기존 부트스트랩 규칙(Manifest 로컬 보장)이 깨지지 않는지 확인

    비고
        본 PR은 “검증 및 다운로드 구현”이 아니라 규칙과 책임 분리의 확정에 초점을 둡니다.
        실제 다운로드 및 교체 로직은 다음 클라이언트 커밋에서 진행합니다.
