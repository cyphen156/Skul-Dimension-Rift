    [Feat][Refactor] Content Sync 플로우 확정 및 ROB 카탈로그/번들 업데이트 규약 완성

변경 요약

    클라이언트 측 콘텐츠 동기화 플로우를 확정하고,
    Manifest → Catalog → Bundle로 이어지는 계층적 업데이트 규약을 완성했습니다.

    Meta 인증 결과를 신뢰의 기준으로 고정한 상태에서,
    Outdated 상황에 한해 RequiredOnBoot(ROB) 카탈로그 및 번들까지
    완전한 최신화가 수행되도록 클라이언트 업데이트 책임 범위를 명확히 정의했습니다.


상세 변경 내용
    1. Content Sync 전체 플로우 확정 (Client)
        ContentManifest Meta 인증을 시작점으로 하는 동기화 플로우 확정
        
        Manifest가 UpToDate일 경우
            → 하위 Catalog / Bundle 검증 및 업데이트를 수행하지 않음

        Manifest가 Outdated일 경우
            → ROB 카탈로그 및 번들 업데이트 수행

    Manifest Meta 인증
        ├─ UpToDate → 전체 콘텐츠 상태 신뢰, 추가 처리 없음
        └─ Outdated → Manifest 본문 갱신
                        → ROB Catalog Meta 인증
                            → Catalog 본문 갱신
                                → Bundle 다운로드 및 갱신

    2. Manifest / Catalog 본문 업데이트 규칙 통합
        Manifest와 Catalog의 본문(Data) 업데이트 규칙을 동일한 정책으로 통합
        Meta가 Outdated일 경우에만 본문 다운로드 수행
        본문 다운로드 성공 시에만 Meta 파일을 로컬에 커밋
        본문 다운로드 실패 시 Meta 갱신을 차단하여
        로컬 상태 불일치 방지

    3. RequiredOnBoot(ROB) 기준 콘텐츠 갱신 규약 확정
        ContentManifest에 정의된 requiredOnBoot == true 카탈로그만
        부트 시점에서 갱신 대상에 포함

        ROB 카탈로그 : 
            Meta 인증, 본문(Catalog) 갱신, 내부 Bundle 전체 갱신과정을
            하나의 트랜잭션으로서 원자적 처리
            다만 번들 다운로드의 경우 부분 업데이트 진행를 지원함

            ROB 처리 중 하나라도 실패 시
                → 전체 업데이트 실패로 간주
                → Meta 커밋 차단

        isContentConsistent 플래그 도입:
            모든 ROB 카탈로그/번들 업데이트 성공 여부 추적
            하나라도 실패 시 false 설정
            false 상태에서는 Manifest Meta 저장 차단
                → 다음 부팅 시 전체 재검증 보장

    4. ContentVerifyContext 기반 상태 전파 구조 유지
        모든 인증/업데이트 결과는 ContentVerifyContext를 통해 전달

        Context는 다음 정보를 단일 객체로 관리
            - 대상 id / schema
            - 인증 결과(UpToDate / Outdated / Failed)
            - 실패 사유
            - 서버 Meta 정보
            - 본문 업데이트 성공 여부

        상위 로직은 Context 결과만을 기준으로 분기하도록 구조 고정

    5. 업데이트 성공 커밋 조건 명확화
        모든 ROB 카탈로그 및 번들 업데이트가 완료된 경우에만
            ContentManifest 본문 저장,
            ContentManifest Meta 저장

        부분 성공 / 중간 실패 상태에서는
            → Meta 및 Manifest 커밋 금지
            → 다음 실행 시 재시도 가능 상태 유지

    6. 체크포인트 기반 부분 업데이트 지원
        Bundle 다운로드는 sha256 기반 파일명으로 저장되어
        네트워크 실패 시에도 이미 완료된 번들은 보존

        Bundle 경로 규칙:
            {persistent}/Bundles/{schema}/{bundleId}/{sha256}.bundle

        재시도 시:
            - 기존 번들 파일 존재 여부 확인 (sizeBytes 검증)
            - 존재하는 파일은 다운로드 스킵
            - 누락된 번들만 재다운로드

        각 Catalog 처리 완료 시 SaveContentMeta(ctx) 호출로
        진행 상황 체크포인트 기록

        이를 통해:
            - 대용량 번들 안전 전송
            - 네트워크 불안정 환경 대응
            - 사용자 중단 후 재개 지원

    7. 무결성 검증 및 구버전 자동 정리
        모든 ROB 콘텐츠 업데이트 성공 후
        C_VerifyAndCleanup() 실행

        처리 과정:
            1. 현재 Manifest의 유효한 Catalog/Bundle 목록 수집
            2. 디스크 스캔하여 목록에 없는 파일 자동 삭제
            3. 빈 디렉토리 정리

        효과:
            - 구버전 콘텐츠 자동 제거
            - 디스크 공간 효율 관리
            - 수동 정리 작업 불필요

    8. 원자적 파일 작업 보장
        모든 파일 저장은 .tmp → atomic move 패턴 사용
        
        저장 흐름:
            1. 데이터를 {path}.tmp에 임시 저장
            2. 기존 파일 존재 시 삭제
            3. .tmp 파일을 최종 경로로 이동

        효과:
            - 저장 중 크래시 발생 시 부분 저장 파일 미생성
            - 파일 손상 방지
            - 항상 완전한 파일만 존재 보장
    책임 분리 상태

        서버 역할
            Meta 제공
            본문(Data / Bundle) 제공

        클라이언트 역할
            Meta 비교 및 인증
            콘텐츠 상태 판정
            본문 다운로드 및 로컬 커밋
            RequiredOnBoot 기준 콘텐츠 최신화 책임
